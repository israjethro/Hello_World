## High-level view

`getChartData()` now treats anything other than literal `'NO'` as not-non-billable, where v1 accepted any truthy value. A typo or unrecognized cell that previously rolled into `nonBillable` now falls outside both buckets, and the JSDoc that explicitly keeps `billableSplit` exposed for external consumers makes the resulting `billable + nonBillable !== totalHours` observable to those consumers. `summarize_()`'s `'YES'`-only check is fine because it never bucketed non-billable.

The `Promise.allSettled` rewrite is correct in mechanics but each of the four slices is independently real-or-mock while the panels read across slices. If `getChartData` fails alone, the 3D bar / doughnut / trend reflect a mock world the cards and table don't share, and the notice naming the failed function doesn't tell the operator that some panels are real and others aren't. The same shape applies to `getMembers` falling back to `MOCK_MEMBERS` while `tasksByMember` is real-keyed by `MEMBER_SHEETS` — equal today but living in two files with no enforced link.

The 3D-vs-2D rendering order (apply 2D unconditionally, then upgrade to 3D only when the `echarts.gl.version` probe passes) is the right shape and closes v1's silent-empty-canvas gap. The remaining hole is selection highlighting: the 2D series builds a per-bar `itemStyle` for `selectedIdx`, but the 3D series passes plain `[i, 0, v]` tuples and a comment promising "per-bar emphasis below" that the code doesn't deliver. v1 issue #8 is fixed for the 2D fallback path and unfixed for the actual 3D path that runs whenever GL loads.

The selection-change reset rules are symmetric in both directions, but search clears unconditionally — including when going back to "All", which loses any in-progress query the user typed before clicking a card. Mild UX cost, traded against the v1 "no match" empty-state confusion. The doughnut label change to `tracked` accepts the under-count rather than widening the buckets, which is defensible since the chart only renders `COMPLETED` / `IN-PROGRESS` slices.

### 3D selection highlight is wired only on the 2D path

The 2D option builds bar items with per-index styling:

```js
data: values.map(function (v, i) {
  var item = { value: v };
  if (i === selectedIdx) {
    item.itemStyle = { color: '#ff6b9a', shadowBlur: 24, ... };
  }
  return item;
})
```

The 3D option does not:

```js
series: [{
  type: 'bar3D',
  data: values.map(function (v, i) { return [i, 0, v]; }),
  ...
  itemStyle: selectedIdx >= 0
    ? { opacity: 1.0 } // base; per-bar emphasis below
    : undefined,
  emphasis: { itemStyle: { color: '#ff6b9a' } }
}]
```

`itemStyle: { opacity: 1.0 }` applies to the whole series and `emphasis` only fires on hover. There is no "per-bar emphasis below" — the comment claims a fix that the code doesn't deliver. echarts-gl's `bar3D` does support per-data-point styling via `{value: [...], itemStyle: {...}}`, so the same pattern as the 2D path is one line away. As shipped, when the GL plugin is loaded (the common case) the user gets no visual feedback that they picked a specific member from the bar chart — the gap v1 issue #8 was meant to close.

### Partial-mock cross-slice inconsistency

The four `Promise.allSettled` outcomes are validated and slotted independently:

```
slice 0 (getMembers)        → state.members
slice 1 (getAllTasks)       → state.tasksByMember
slice 2 (getAllSummaries)   → state.summaries
slice 3 (getChartData)      → state.chartData
```

The panels read across these:

- KPI cards: `state.members` × `state.summaries` (with mock-fallback to `state.tasksByMember`)
- Table: `state.members` × `state.tasksByMember`
- 3D bar: `state.chartData.hoursPerMember`
- Doughnut: `state.chartData.statusBreakdown` (or recompute over `tasksByMember` for single-member view)
- Trend: `state.chartData.hoursPerDay`

A `getChartData`-only rejection produces real cards/table and a mock 3D bar/doughnut/trend that reflect a different (sample) dataset. The notice text — "Using sample data for: getChartData: <reason>" — names the failed call, which an Apps Script reader can translate to "the charts", but a non-developer reading the dashboard sees the message and may assume the whole UI is sample. The same applies to `getAllSummaries` rejecting alone (cards mocked, charts real) and to `getMembers` rejecting alone (member list mocked, every other slice keyed by real names).

This is strictly better than v1's all-or-nothing collapse, but the partial-mock state is not made legible. Two reasonable fixes: expand the notice to name affected panels rather than function names, or treat any `chartData` / `summaries` rejection as "fall back the whole UI to mock" since the per-panel decoupling is observable but not communicated.

### Billability bucketing tightened

`getChartData()` is asymmetric:

```js
if (r.billability === 'YES') billable += h;
else if (r.billability === 'NO') nonBillable += h;
```

The pre-v2 form was `if 'BILLABLE' { billable } else if (r.billability) { nonBillable }` — the second branch caught any truthy non-`'BILLABLE'` value, including the actual sheet's `'YES'` and `'NO'`. After the fix, only literal `'NO'` counts as non-billable:

| Cell value (post-`upperTrim_`) | v1 `nonBillable` | v2 `nonBillable` |
|---|---|---|
| `'YES'` | counted (bug) | not counted (fixed) |
| `'NO'` | counted | counted |
| `''` (empty) | not counted | not counted |
| `'N/A'`, typo, etc. | counted | **not counted** |

The fourth row is the new asymmetry: any unexpected non-empty value drops out of both buckets, so `billable + nonBillable < totalHours`. v1 issue #3 was justified on the grounds that `billableSplit` is computed in the same single pass and exposed for external `getChartData` consumers — but those consumers will now see split-totals that don't reconcile to `totalHours` whenever the sheet contains anything outside the documented `YES`/`NO` convention. Either coerce non-`'YES'` to non-billable (matching `summarize_`'s implicit "everything else is not billable") or add a JSDoc warning that `billableSplit` only reconciles when the sheet strictly uses `YES`/`NO`.

### MOCK_MEMBERS / MEMBER_SHEETS are equal-by-hand

`Code.gs` declares `MEMBER_SHEETS = ['Isra','Sowmiya','Keerthana','Yogesh','Tamizharasi']`. `Javascript.html` declares `MOCK_MEMBERS = ['Isra','Sowmiya','Keerthana','Yogesh','Tamizharasi']`. The partial-mock fallback for `getMembers` only produces a coherent UI while these two lists are equal: every other slice (server-real or mock) is keyed by these names, so the cards/table/charts iterate `state.members` and look up `tasksByMember[name]`, `chartData.hoursPerMember[i].member`, etc. If someone edits the team roster in `Code.gs` and forgets the mock, a `getMembers` failure renders mock names against real data (or vice versa) with empty cards across the board. A short cross-reference comment in both files, or deriving the member list from `tasksByMember` keys when the dedicated slice fails, closes that gap.

### Test coverage

No test infrastructure was added (none exists in the project, per `context.json`); none was expected for v2. The billability asymmetry above is exactly the kind of drift a single `summarize_` / `getChartData` unit test would have caught — `summarize_` against a `YES`/`NO` row set and a `getChartData` reconciliation check (`billable + nonBillable === totalHours` for known inputs) would have flagged the new bucketing gap before this pass.
