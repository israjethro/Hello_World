# QA Daily Status Dashboard — Apps Script web app (v1)

A new `apps-script/` project that renders the team's "QA - Daily Status" sheet (5 member tabs) as a glass-themed dashboard with KPI cards, three ECharts charts, and a sortable/searchable task table. The server side (`Code.gs`, `DataService.gs`) reads each tab, normalizes dates and numbers, builds per-member summaries and chart-shaped payloads, and routes every public read through `CacheService` with a 60s TTL. The client (`Index.html` + 3 partials) fans out four `google.script.run` calls in parallel, falls back to a built-in MOCK if the bridge is unavailable or any call fails, and is wired so a member selection re-filters all charts and the table at once. Java files under `src/` and class files under `bin/` are untouched (verified via `git diff 86bbb57..HEAD -- src/ bin/`, empty).

**Watch for:** (confirmed) the server's billability check is `'BILLABLE'` against a sheet that stores `'YES'`/`'NO'`, which silently zeroes `summary.billableHours` and `chartData.billableSplit.billable` on real data; (confirmed) `getAllSummaries` is one of four blocking server calls but its result is never rendered — cards recompute from raw rows; (confirmed) the 3D-bar fallback only fires if `setOption` throws, which ECharts often doesn't do for unregistered series, so a CDN failure for `echarts-gl` can leave a blank canvas; (confirmed) `Promise.all` short-circuits, so any single rejected call swaps the entire dashboard to mock; (confirmed) the deployment manifest opens this dashboard to `ANYONE_WITH_GOOGLE` and `ALLOWALL` X-Frame, which combined with team-status data is worth a deliberate decision.

## High-level view

A missing tab is caught per-member inside `getAllTasks`/`getAllSummaries`/`getChartData` so one bad tab doesn't take down the dashboard, but the affected member silently shows zeros with no operator-visible signal — a renamed or deleted tab will look like an idle member.

The biggest server bug is a constant mismatch: `summarize_()` and `getChartData()` both compute billable hours by checking `r.billability === 'BILLABLE'`, but `upperTrim_` produces `'YES'` / `'NO'` from the actual sheet. The client compensates by re-deriving `Billable Hrs` from raw rows in `buildSummary()` with a top-of-file comment flagging it. The workaround is fragile — `chartData.billableSplit.billable` stays wrong on the server (always 0), and any future caller that trusts `getMemberSummary`/`getAllSummaries` reads zero billable hours. Fixing the server check to `'YES'` is the right call; the client recompute should then go away.

The render pipeline has a related dead-data problem. `init()` blocks on four `Promise.all` reads — `getMembers`, `getAllTasks`, `getAllSummaries`, `getChartData` — but `state.summaries` is assigned and never read by any render function (verified via grep), and `chartData.billableSplit` and `chartData.bugsPerMember` are computed server-side but never consumed by the client. The KPI cards recompute everything from `state.tasksByMember` via `buildSummary()`. So the slowest of the four server calls is paid for nothing, and because `Promise.all` short-circuits on first rejection, a failure of `getAllSummaries` (or any other) drops the entire dashboard to MOCK even though the data the client actually needs may have arrived.

The 3D-bar CDN-failure fallback is not robust. The `canBar3D` probe collapses to `hasGl`, which is true if the `<script src="…echarts-gl">` tag is present in the DOM regardless of whether the script actually loaded. The real safety net is the `try { setOption(option3d, true) } catch` around the 3D option, but ECharts typically logs a warning rather than throwing for an unregistered series type (`bar3D`, `grid3D`), so a network failure on the GL plugin can leave a silent empty canvas and never reach the 2D fallback path.

Selecting one member reduces the 3D bar to a single bar, which removes the team-load comparison the chart exists for. The doughnut's center label sums only `COMPLETED` + `IN-PROGRESS`, so any other status value in the sheet is silently dropped from the count and the big number under-reports total tasks. The table-cell rendering for `noOfBugs` outputs both the bare number and a badge with the same number inside, displaying e.g. `2 ⓶`.

The web-app exposure is `access: ANYONE_WITH_GOOGLE` + `executeAs: USER_DEPLOYING` + `setXFrameOptionsMode(ALLOWALL)`. Combined, that means anyone with a Google account who knows the URL can read team daily-status records under the deployer's identity, and any site can iframe the page. The README does not call out that trade-off. The `script.external_request` scope is listed and explained in the README as needed to load ECharts, but ECharts loads in the user's browser, not via `UrlFetchApp` — the scope is unused by the current code. The README also claims that "Saving invalidates the script cache"; `CacheService` entries persist across saves and redeploys until TTL expiry or explicit `removeAll`.

### Billability mismatch and the client-side compensation

```js
if (r.billability === 'BILLABLE') {
  billableHours += toNumber_(r.hours, 0);
}
```

`readMemberRows_` builds `r.billability` via `upperTrim_(row[5])`, and the sheet stores literal `'YES'` / `'NO'`. So on real data, `billableHours` is always 0 in `getMemberSummary` and `getAllSummaries`, and `getChartData().billableSplit.billable` is always 0 too — the same constant is wrong in both spots.

The client compensates only for the cards: `Javascript.html` calls `buildSummary(name, rows)` which checks `String(r.billability || '').toUpperCase() === 'YES'`. That keeps the cards correct but leaves `state.summaries` and `chartData.billableSplit` quietly wrong. Both are currently unread by any render path, so users don't see the bug — but `getAllSummaries` is still fetched on the critical render path, and any future consumer who trusts those fields will silently get zeroes.

The clean fix is on the server (`'BILLABLE'` → `'YES'` in both functions, optionally `'NO'` for `nonBillable`). After that, the client `buildSummary` recompute can be deleted and cards can render from `state.summaries[i]` directly. Keeping the workaround long-term means two billability rules to maintain.

### Dead server payloads on the critical path

`init()` blocks on:

```js
Promise.all([
  runServer('getMembers'),
  runServer('getAllTasks'),
  runServer('getAllSummaries'),
  runServer('getChartData')
])
```

Searching `Javascript.html` for downstream reads:

- `state.summaries` — assigned in both the success and catch paths, never read.
- `chartData.billableSplit` — produced server-side, never read.
- `chartData.bugsPerMember` — produced server-side, never read.

`getAllSummaries` is pure overhead, and roughly half of `getChartData`'s payload is computed and never rendered. The cost is paid twice: once in spreadsheet read time (each call iterates all five tabs) and once in `Promise.all` blocking the first paint until the slowest of the four arrives. Combined with the short-circuit behavior below, an outage in any of these unused paths takes down the rest of the UI.

### Promise.all short-circuit collapses to MOCK

A transient `getAllSummaries` error (e.g., quota or a one-tab read hiccup) causes the entire `.catch` to run, which sets `state.usingMock = true` and replaces `tasksByMember` and `chartData` with mock data even though those reads may have actually succeeded. The "Showing sample data" notice then misleads the operator about which subsystem broke. `Promise.allSettled` would let each slice fall back independently — only the rejected calls go to mock, and the notice can name the specific subsystem.

### 3D-bar fallback only fires on a thrown setOption

```js
var hasGl = !!(echarts.gl || (echarts.registerVisualMap && window.echartsGlLoaded)) ||
            typeof echarts.GL !== 'undefined' ||
            !!document.querySelector('script[src*="echarts-gl"]');
var canBar3D = false;
try {
  canBar3D = !!(echarts && echarts.registerComponentModel === undefined ? hasGl : hasGl);
} catch (e) { canBar3D = false; }
```

The last branch is `hasGl ? hasGl : hasGl` — a tautology. The `<script>` tag is hard-set in `Index.html` regardless of network outcome, so `hasGl` is essentially always true at runtime. The fallback then depends entirely on the `try { charts.chart3d.setOption(option3d, true) } catch` block; if ECharts handles the unregistered `bar3D` series type by logging a warning and rendering nothing (its common behavior), `success` becomes `true`, the 2D fallback is skipped, and the chart card shows an empty canvas.

A more direct probe is to attempt a single zero-size init with a `bar3D` series in a try/catch that explicitly checks the result, or to test for one of the GL-registered components after init. Even simpler: render the 2D bar by default and only attempt the 3D upgrade when a known marker (e.g., `echarts.gl && echarts.gl.version`) is present.

### Selection-change behavior

Selecting one member filters `chart3d`'s data array to length 1. The chart's purpose ("team load distribution") relies on showing all five bars; a single bar with no comparison is uninformative. A common pattern is to keep all members in the series and use `emphasis` styling or a brighter `itemStyle` on the selected index, leaving the comparison context visible.

`computeStatusBreakdown()` only counts `COMPLETED` and `IN-PROGRESS`, so the doughnut center label `'{big|' + total + '}\n{small|tasks}'` is the sum of those two buckets only. Any other status value drops out silently, and the user-facing claim "N tasks" under-reports.

### Table rendering rough edges

```js
} else if (c.key === 'noOfBugs') {
  var n = Number(v) || 0;
  td.innerHTML = n > 0
    ? escapeHtml(String(n)) + '<span class="bug-badge" title="bugs">' + n + '</span>'
    : '<span class="billable-no">0</span>';
}
```

For `n=2` this renders the literal `2` followed by a circular badge containing `2` — the number is shown twice. Render either the bare number (no badge) or the badge alone.

`state.sort.key` is module-scoped and survives selection change. Under "All", `getColumns()` adds a `member` column at index 1; sorting by `member` and then selecting a single member removes that column from `cols` but leaves `state.sort.key === 'member'`. `applySearchAndSort` then can't find the column, defaults to `type: 'text'`, sorts on `r.member` which is `undefined` for every row (single-member rows are built without the `{member: m}` spread), and the table appears unsorted with no indicator. Reset `state.sort` to a column that exists in the new view on transition.

Search persists across selection change (`state.search` and the input value both survive). The empty-state copy says `'No tasks match "<search>"'`, so a user who selects a sparse member after a broad search may see "no match" instead of that member's actual rows.

### Sheet I/O edge cases

`Math.max(sheet.getLastColumn(), ROW_WIDTH_)` reads ten columns even if the sheet has fewer. New Sheets default to 26 columns so the `getRange(3, 1, lastRow-2, 10)` is normally safe, but if someone explicitly trims the tab below ten columns Apps Script raises a `Range exceeds bounds` error and `readMemberRows_` throws. `getAllTasks` catches that into `[]` per member, but `getMemberTasks` (single) does not — the public function would surface the raw error to the client.

`getAllTasks` catching missing-tab errors into `[]` is the right per-member isolation, but the operator never sees that a tab disappeared — the affected member's KPIs and chart entries silently go to zero. A `Logger.log` or a per-member error field on the response would close that observability gap.

### Cache strategy

`withCache_` keys on `fnName + JSON.stringify(args)`, TTL 60s, falls through to a fresh read on cache-read failure, guards against the 100KB ScriptCache limit by skipping puts ≥95KB, and swallows put errors. Stale data of up to 60s during active sheet edits is documented in the README.

Five public functions all iterate the same five tabs, so per-function keying means each of `getAllTasks`, `getAllSummaries`, `getChartData` does its own pass instead of sharing a single normalized rows snapshot. Not a bug, just observable cost — and one more reason to drop the `getAllSummaries` call entirely per the dead-fetch concern above.

### Web-app exposure and OAuth posture

```json
"webapp": {
  "access": "ANYONE_WITH_GOOGLE",
  "executeAs": "USER_DEPLOYING"
}
```

`doGet` sets `setXFrameOptionsMode(HtmlService.XFrameOptionsMode.ALLOWALL)`. Together, anyone holding a Google account who learns the URL can read team daily-status records under the deployer's identity, and any external site can iframe the page (clickjacking surface). For an internal QA dashboard this is permissive; the README doesn't flag the trade-off. Tightening to `MYSELF` (bound) or `DOMAIN` and `XFrameOptionsMode.DEFAULT` is one option; explicitly documenting the choice is the other.

`script.external_request` is listed in the manifest and the README justifies it as "load the ECharts library from its CDN" — but the scope governs server-side `UrlFetchApp`, not browser fetches. The code makes no `UrlFetchApp` call, so the scope is unused and can be removed; the consent screen will then list one fewer permission.

### README accuracy

The `script.external_request` justification ("load the ECharts library from its CDN") confuses browser CDN fetches with server-side `UrlFetchApp`. The scope governs the latter, which the code doesn't use.

The cache-busting advice ("Saving invalidates the script cache and serves a fresh read on the next request") is incorrect — `CacheService` entries survive saves and redeploys until TTL expiry or explicit `removeAll`. Replace with: wait 60s, call `CacheService.getScriptCache().removeAll([...keys])` from the editor, or temporarily lower `CACHE_TTL_SECONDS_`.

### Test coverage

There is no test infrastructure in this project (documented in `context.json`) and none was added. The unit-testable units — `normalizeDate_`, `isEmptyRow_`, `summarize_`, `mapToSortedSeries_`, `applySearchAndSort`, `buildSummary` — would benefit from at least a small harness because the date and billability normalization rules are exactly the kind of thing that drifts; the billability bug would have been caught immediately by a `summarize_` unit test.

Not tested: behavior on a sheet with only header rows; behavior on a tab whose date column contains mixed `Date` objects and strings; behavior of the GL plugin failing to load; selection-change correctness across all surfaces; bug-cell rendering.
